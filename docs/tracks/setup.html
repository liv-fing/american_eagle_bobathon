7
Understanding Bob Modes
Note: This step is only to help you learn about Bob modes. Nothing on your end needs to be completed.
Bob comes with 3 modes, and the Premium Package for i adds 2 more. In total, you will have 5 modes that Bob can use.
A mode is like a job description for Bob. It tells Bob two things: how to act (its role and expertise), and what it is allowed to touch (its permissions). Switching modes is like giving the same assistant a different job.
Bob comes with 3 default modes:
1) Agent Mode
Role (the doer): Turns an idea or plan into working code. Use it to write, change, or refactor code, implement features, and fix bugs.
Permissions: Broadest. It can read, edit, and run commands.
2) Plan Mode
Role (the architect): Analyzes requirements and designs the steps before any code is written.
Permissions: It can read, but it can only edit Markdown and text files — meaning it cannot edit any coding files. It can write a plan, but it cannot change your code.
3) Ask Mode
Role (the explainer): Answers questions and explains code without making changes.
Permissions: Read only.
💡 Tip: Want to understand code? Use Ask. Want a plan first? Use Plan. Ready to build? Switch to Agent.
IBM i specific modes: The IBM Bob Premium Package for i adds two IBM i specialist modes. They already know IBM i terms and best practices, so you don't have to explain the platform to Bob. At the start of each task, Bob automatically receives your connection details, OS version, CCSID settings, and library lists.
1) IBM i Developer Mode
Role (the IBM i programmer): Explains, generates, compiles, tests, and documents code on IBM i. It works with RPG (OPM and ILE), SQL on Db2 for i, CL, DDS, and COBOL.
Typical tasks: Explain or document program logic, write or refactor source code, compile objects, generate and fix RPG unit tests, plan modernization, convert fixed-format RPG to free-format.
Permissions: Read, edit, execute, MCP, todo, subtask, and skill.
2) IBM i Database Mode
Role (the Db2 for i specialist): Generates, modernizes, tunes, and reviews SQL on Db2 for i. It checks for correctness, performance, security, and IBM i best practices. It also helps you understand complex database schemas and analyze query performance and indexes.
Permissions: The same as IBM i Developer, except it does not include MCP.
💡 Tip: Use IBM i Developer for code work. Use IBM i Database for SQL and schema work.

0.4 — Save and Prepare Your Private Key

In this step, we are linking the SSH key with the server to make a connection. Your instructor has sent you a zip file. Double-click it to open it. When it asks for a password, enter the password your instructor gives you. After you enter it, you will see a .pem key file. Save it somewhere you can find it, because you will use this private key to connect Bob to IBM i.

1
Extract the encrypted private key archive
Your instructor has provided a password-protected zip file containing your private key. Double-click the zip file, and you will be prompted to enter a password. Enter the password your instructor gives you. This should leave you with the ae_primary_key.pem file, which is the private key you will use to connect to your IBM i server for today's lab.
💡 Tip: Keep ae_primary_key.pem in a known folder on your computer (such as your Downloads folder) so you can easily browse to it when connecting.
💡 Key permissions: You don't need to change anything on the key file now. If you reach Lab 4 and SSH reports UNPROTECTED PRIVATE KEY FILE, follow the key-permissions fix (T2, mostly Windows) in the Lab 4 Troubleshooting section.

While still in the Code for IBM i extension, go to the Object Browser section and click the funnel icon or the Create new filter button.
Object Browser — click the funnel icon or Create new filter
